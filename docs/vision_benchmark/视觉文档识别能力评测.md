# qwen2.5vl:7b 文档类图像识别能力评测

> 评测日期：2026-09-21
> 被测模型：`qwen2.5vl:7b`（本地 Ollama，8GB 单卡）
> 评测链路：项目真实 `core/llm/vision_plugin.py` → `VisionPlugin.recognize_images()`
> 调用参数：`temperature=0.1`、`num_predict=2048`、`keep_alive=5m`、单图串行
> 运行次数：**2 轮**（冷启动 1 轮 + 预热后 1 轮），用于暴露输出波动

## 一、评测目的

回答一个具体问题：**这个 7B 本地多模态模型，对 PPT / Word / Excel 这类文档图像的真实识别能力到底如何？**
（PPT/Word/Excel 截图转 Markdown 是本项目未来必须重点支撑的场景）

## 二、样本构造

为可复现与可比对，样本用 `gen_doc_images.py` 以程序化方式渲染，内容与项目自身领域一致（避免"背题"偏差）。

| 编号 | 文件 | 尺寸 | 难度设计 |
|---|---|---|---|
| 1 | `01_ppt.png` | 1280×720 | PPT 风格：横幅标题 + 二级标题 + 4 条项目符号 + **3 列 × 4 行表格** |
| 2 | `02_word.png` | 1000×1250 | Word 风格：H1 + 段落（跨 3 个视觉行）+ H2 + 有序列表 + **表注 + 2 列 × 4 行表格** |
| 3 | `03_excel.png` | 1080×470 | Excel 风格：**6 列 × 7 行**，中文表头 + 小数 + 单位符号 |
| 4 | `04_excel_lowres.jpg` | 540×235 | 第 3 张的劣化版：**分辨率减半 + JPEG q42**，模拟手机拍屏/二次压缩 |

样本 2 的"表注 + 表格"结构、样本 4 的劣化处理，均刻意设计为**"识别正确但格式易错"**的陷阱。

## 三、实测结果

### 3.1 延迟

| 样本 | 冷启动耗时 | 预热后耗时 | 输出字符数 |
|---|---|---|---|
| `01_ppt.png` | 12.8 s | 6.1 s | 375 |
| `02_word.png` | 8.1 s | 6.0 s | 389 / 386 |
| `03_excel.png` | 6.5 s | 5.4 s | 345 |
| `04_excel_lowres.jpg` | 6.4 s | 5.3 s | 343 / 331 |

**结论：单图 5.3 ~ 12.8 s**（冷启动含模型加载）。对该场景完全可用。

### 3.2 内容正确性 —— 全部正确，且高度稳定

以 2 轮 × 4 样本 = **8 次识别**为分母统计：

| 评测维度 | 结果 |
|---|---|
| 中文字符还原 | ✅ **8/8 全对** |
| 英文字符还原 | ✅ **8/8 全对** |
| 数字 / 小数还原 | ✅ **8/8 全对**（样本 3/4 各 42 个数字） |
| 特殊符号（≥、<、→、全角括号） | ✅ **8/8 全对** |
| 项目符号 / 有序列表 | ✅ **8/8 全对** |
| **表格结构重建** | ✅ **8/8 全对**（含 6×7 密集表） |
| 跨行段落合并 | ✅ **2/2 正确**（3 个视觉行合并为 1 段） |
| 内容幻觉 / 增删 | ✅ **0 次** |

**这是本次评测最重要的结论：内容层面零错误，且两次运行的文字内容完全一致。**

### 3.3 劣化鲁棒性

样本 4 把样本 3 **降到 540×235（约原图 1/6 像素）再用 JPEG q42 强压缩**。
结果：**6 列 × 7 行共 42 个单元格，两轮均无一出错**，文字与全分辨率版本完全一致。

### 3.4 格式契约 —— 这才是真正的问题，且**不稳定**

同样的图片、同样的参数（`temperature=0.1`），两轮输出在**结构标注**上出现差异：

| 缺陷 | 出现次数 | 具体表现 |
|---|---|---|
| 整个输出被 ```markdown 代码围栏包裹 | **7/8** | 提示词从未要求；第 2 轮样本 4 未出现 |
| 标题层级标注不一致 | **6/8 不稳定** | 同为显著标题：样本 1 两轮均为**纯文本**（无 `#`）；样本 2、3 两轮均为 `#`；样本 4 第一轮纯文本、第二轮变成 `###` |
| 表注被升级为标题 | **1/8** | 样本 2 第一轮输出 `## 表 4-2 补丁处理策略对照`（凭空多出章节）；第二轮为纯文本，正确 |
| 全角标点转半角 | 8/8 | `：` → `:` |

**关键判断：内容稳定，格式不稳定。** 在 `temperature=0.1` 下仍出现结构性波动，说明这不是采样随机性，而是模型对"视觉层级 → Markdown 层级"的映射本身缺乏确定性。

## 四、结论

### 4.1 结论一："本地 7B 识图很笨"这一担忧，在文档场景下不成立

- 文字级 OCR（中英数字符号混合）**8/8 零错误**
- **表格结构重建 8/8 零错误**——这是 VLM 最容易翻车的地方，而它在 6×7 的密集数字表上全对
- 对分辨率劣化**高度鲁棒**（1/6 像素 + 强压缩仍全对）

**PPT / Word / Excel 这条线（未来必须重点支撑的场景）本身是可以放心依赖的。**

### 4.2 结论二：不能依赖模型产出稳定的结构，必须在工程侧收敛

格式层的四个缺陷中，**没有一个能靠"换个更大的模型"解决得比"加一段确定性后处理"更省**。尤其标题层级在两次运行间从"无"跳到"###"，意味着任何依赖 `#` 数量做分页/分级的导出逻辑（如 `convert_to_pptx` 按 H2 分页）都可能拿到不确定输入。

### 4.3 修复建议（均确定性、可回归验证）

| # | 建议 | 类型 | 优先级 |
|---|---|---|---|
| A | 剥离最外层代码围栏（正则匹配 ```lang ... ``` 整段包裹） | 后处理 | **高**（7/8 命中，且会导致最终 Markdown 被整体渲染成代码块） |
| B | 提示词显式补充：① 不要用围栏包裹整个输出；② 仅当原图文字本身呈明确标题层级时才用 `#`，表注/图注/页脚不要升级为标题 | 提示词 | 中 |
| C | 在导出层（`core/export/converter.py`）做一次标题规范化，消除上游不确定性 | 导出层 | 中 |
| D | 若对结构稳定性有硬要求，可考虑固定格式模板 + 约束解码，而非自由 Markdown | 架构 | 低（成本高） |

建议 A 是**确定性的、零副作用的**，可直接落地；B 需配合一次回归（重跑本评测比对）。
