### 2.1 `agents/summary/agent.py` → 舍弃

**职责**：它是 Knowledge 与 Writer 之间的中间态。做法是 `_parse_knowledge_output()` 用正则去抓
Knowledge 输出里的 `【领域知识】` / `【通用知识】` 段（`agent.py:94,118`），再抽关键词、
需求点、按任务类型套固定大纲。

**为什么可以删（三条独立证据）**：

1. **职责已被显式搬走**。`agents/knowledge/agent.py:17` 的注释原文：
   `# 任务类型模板（原 Summary Agent 的 outline 功能）`——作者自己把 outline 功能迁到了 Knowledge。
   Knowledge 现在直接产出 `requirements`（`:857`）和结构化 JSON（`:860-876`）。
2. **它依赖的输出格式已经不存在**。它正则匹配的 `【领域知识】` 区块，在现役 KnowledgeAgent
   的输出里已经不再生成（`structured_json` 取代了文本块），所以它不单是「没被调用」，
   是**调用也解析不出东西**。
3. **零引用**。`SummaryAgent` 全仓只出现在类定义处；`agent_registry` 只注册
   `knowledge/writer/review/judge/result` 5 个（`agents/base/agent_registry.py`），
   而 `contract.REQUIRED_AGENT_IDS` 也正好是这 5 个。

**删除动作**：删文件 + 删 `agents/summary/`（若空）。

### 2.2 `services/` 包 → 舍弃

**职责**：`AgentService` 是一个「什么都装」的早期门面——把 `AgentRegistry`、
`WorkflowService`、`DynamicRouter`、`KnowledgeService`、`MetricsStore` 聚成一个单例，
再暴露 `execute_workflow / search_knowledge / route_request / get_metrics`。

**为什么可以删**：现役架构里这些能力由 `api/v1/*/router.py` 各自直接持有，
生命周期由 `app/main.py` 的 lifespan 管理；`get_agent_service()` 全仓零调用
（实测 grep：只有 `services/__init__.py` 自己引用自己）。

**删除动作**：删 `backend/services/` 整包。

### 2.3 `knowledge/service.py` → 舍弃（**这个最该处理，它有实际危害**）

**职责**：一个「关键词 → 句子列表」的 JSON 字典 + 子串检索 + `SimpleCache`。
路径写死 `knowledge/knowledge_base.json`。

**为什么该删**：

1. **在役实现是另一个同名类**：`knowledge/mysql_service.py:48` 定义了
   `class KnowledgeService`（SQLite 后端），`get_knowledge_service()` 是现役入口，
   `agents/knowledge/agent.py:417` 和 `api/v1/knowledge/router.py:5` 都用它。
   **两个类同名、两份职责** —— 这是最容易让答辩老师追问「到底哪个在用」的坑。
2. **`knowledge/__init__.py:1` 导出的却是旧的那个**：
   `from .service import KnowledgeService` / `__all__ = ["KnowledgeService"]`。
   任何 `from knowledge import KnowledgeService` 都会拿到旧实现。这是**误导性导出**。
3. **它给测试提供虚假信心**：`tests/test_api/test_knowledge_api.py` 4 个用例
   测的全是旧实现（断言 `"AI" in results` 命中的是硬编码内置字典），
   跑绿了也**完全不反映生产知识库**。
4. **它是测试污染源**：`_save_knowledge_base()` 无 `makedirs` 保护地直写仓库内文件，
   实测跑一次全量测试即把 `backend/knowledge/knowledge_base.json` 整文件重写。

**删除动作**（三步，缺一不可）：
1. 删 `knowledge/service.py`
2. 改 `knowledge/__init__.py` → 导出 `mysql_service` 的 `KnowledgeService` / `get_knowledge_service`
3. 重写 `tests/test_api/test_knowledge_api.py` 指向 `knowledge.mysql_service`
   （用 `tmp_path` 注入数据库路径）

### 2.4 上下文压缩三件套 → **重连**（不是废弃，是半拉子工程）

**职责**（读代码确认，三者职责清晰、彼此解耦、设计完整）：

| 文件 | 职责 | 关键接口 |
|---|---|---|
| `context_token_counter.py` | 中英文混合 token 估算 + 上下文占比 + 阈值判定 | `TokenCounter.estimate()`、`ContextUsage.is_over_threshold` |
| `context_round_recorder.py` | 每轮结束抽取「需求 / 解决了什么 / 改动了什么」 | `RoundRecorder.record_round(sandbox_id, user_input, workflow_output)` |
| `context_compressor.py` | 超阈值时把历史压成 markdown 摘要注回消息列表，保留最近 3 轮 | `ContextCompressor.compress(sandbox_id, messages, system_prompt)` |

**判据 —— 为什么是「重连」而不是「舍弃」**：

- 这套代码**读的字段与真实 workflow 输出完全对得上**
  （`workflow_output["steps"][i]["agent_id"/"output"/"success"]`、`final_result`），
  说明设计时确实按真实链路对过接口，不是凭空写的。
- 前端**已经建好了消费端**：`frontend/src/components/layout/DashboardLayout/components/`
  下有 `ContextBar.tsx`、`ContextPanel.tsx`、`ContextOverflowModal.tsx`、`MetricsBar.tsx`。
- **但后端 `api/` 目录里没有任何 `/context` 端点**（实测 grep `compressor|token_counter|context/usage` → 0 命中）。
  云端 8-18 的提交信息自己承认了：「修复缓存命中率/上下文面板数据源（**改用 chatHistory 本地计算**）」
  —— 即后端压缩链路被放弃，前端改成自己估。
- **后果是实的**：本地模型上下文窗口有限（8GB 显存下 4K），长对话溢出时**没有任何后端兜底**，
  历史直接丢。这正是「上下文管理」这个卖点该解决的问题。

**重连方案（3 步，可独立验证）**：

1. **记录**：在 `WorkflowService` 每轮结束（`service.py` 现有 `_update_*` 附近）调用
   `get_round_recorder().record_round(sandbox_id, original_user_input, workflow_output)`。
   风险：极低（纯内存字典，按 sandbox_id 隔离，已有 `clear_sandbox`）。
2. **暴露**：新增 `GET /api/v1/context/usage?sandbox_id=`，返回 `TokenCounter` 的估算与阈值，
   前端 `ContextBar`/`ContextPanel` 换成真实数据源（替换本地估算）。
3. **压缩**：在 Writer / Result 组装 messages 之前，若 `ContextUsage.is_over_threshold`，
   调用 `get_compressor().compress(...)` 注入 markdown 摘要。
   验证：构造 20 轮超长对话，断言压缩后 token 下降且最近 3 轮完整保留。

### 2.8 `contract.py::guard_io` → 重连

**职责**：与 `guard_llm_call` 完全对称的 **IO 边界记账器**。
`guard_llm_call` 已挂载（`BaseAgent._call_llm`），所以 LLM 越界会被记账/拦截；
但 `guard_io(agent_id, resource)` **全仓从未被调用**（实测 grep），
于是「越界账本」里永远只有 LLM 维度、没有 IO 维度。

**现状的实际影响**：契约里声明的 `io_resources`（如 Knowledge 声明含 `WEB`/`DATABASE`/`FILESYSTEM`、
Result 声明含 `CLOUD_API`）目前**纯属文档**，运行期不产生任何约束与观测。

**重连方案**（低风险，`guard_io` 设计上只返回 bool 不抛异常，符合本项目 DEGRADED 语义）：
在 KnowledgeAgent（WEB / LOCAL_INDEX / DATABASE / FILESYSTEM）、Writer（OLLAMA_GPU / FILESYSTEM）、
Result（CLOUD_API / FILESYSTEM）的实际 IO 调用点前插入
`if not guard_io("knowledge", IOResource.WEB): <走降级路径>`。
配合 CI 里的 `AGENT_CONTRACT_STRICT=1`，越界会立刻暴露。

### 2.9 IntentGraph 消费（`should_intervene`）→ 重连，降级为软节流

**职责**：`KnowledgeRecommendationEngine.should_intervene(intent_graph)` 读 IntentGraph，
判断「是否连续 N 次同领域提问」，作为「要不要弹提示词模板推荐」的节流阀。

**现状**：`core/workflow/service.py:386` 处**绕过**它直接调用 `recommend()`
（`:393` 注释原文「不经过 should_intervene 判断」），`service.py:369` 的注释自述理由：
「IntentGraph 连续 3 次介入策略在实际使用中难以触发（重启清空、领域不一致），
改为只要 Decomposer 匹配到节点就推荐」。

即：**IntentGraph 在记录（`service.py:905 intent_graph.record(...)`），但没有任何消费者，
`should_intervene` 只在 `tests/test_phase6.py` 里被调用过（6 个用例）。**

**为什么不该简单删掉 `should_intervene`**：
IntentGraph 是 README「Graph First, Engine Second」四大图之一；把一个「记录但不消费」的图
直接删掉，等于承认这条叙事是空的。而它的原始意图（避免每次都推模板、按领域连续性分级）
是合理的，只是**触发条件定得太苛刻**（要求连续3次 + 领域一致 + 不重启）。

**重连方案（保留意图，放宽触发）**：
把 `should_intervene` 从「开关」改成**优先级/冷却信号**：
- 首次命中：仍立即推荐（保留前端体验，不倒退）
- 用 IntentGraph 的领域连续计数决定：连续 ≥2 次同领域 → 推荐置顶 + 跳过冷却；
  跨领域切换 → 走正常冷却（`skip_next_recommend`）
即「旁路」变「加权」。这样图真正参与决策，且不会退化成"每次都一样的推荐"。

**若你更想收敛**：那就把 `should_intervene` 连同 `tests/test_phase6.py` 的 6 个用例一起删，
并把 README 的四图表述改成「三图 + IntentGraph 仅做记录」。**二选一，不建议维持现状。**

### 2.10 `learning_engine._deepseek_analyze` → 重连

**职责**：自学习链路里，当本地 `find_similar_node()` 判定「该概念与已有知识无关联」时，

**现状**：`learning_engine.py:377-388` 是纯 TODO，恒 `return None`
（`self.deepseek_enabled = True` 但函数体只有日志 + return）。
结果是**无关联概念一律放弃学习**——自学习闭环在「拓新」这一半是关着的。

**为什么现在重连成本低**：云端调用已统一到 `core/llm/client.generate_cloud()`
（模型读 settings = `deepseek-flash`），不存在新增通道的问题。

**重连方案 + 成本护栏**：
- 用 `generate_cloud()`，提示词约束为「只判断该概念是否值得入库，输出 JSON：
  `{worth_learning, definition, domain, confidence}`」，**不做自由生成**
- 三重门槛（防止烧钱）：① 仅 `find_similar_node() is None` 时触发；
  ② `concept` 长度 ≥ 4 且非纯数字/符号；
  ③ 单轮 workflow 内最多 1 次
- 产出**仍然进 pending 队列**由人工审批，不直写图谱（符合「知识类全落待审」的既有约定）

### 3.2 新修的真实缺陷：领域难度表在生产中完全不可达

`ReviewEngine._calculate_difficulty` 旧实现 `domain = skill_path[-1]`，
而 `difficulty_matrix.yaml` 的 `domain_base_difficulty` 是嵌套结构
（`tech: {base:0.45, ai:{base:0.55, agent:{base:0.60}}}`）。
叶子名既不是顶层键也不是完整路径 ⇒ `_lookup_domain_difficulty` 返回 `0.0`
⇒ **整张表在生产中从未被命中过**。

实测：`skill_path=["root","tech","ai","agent"]` 时 `base=0.00`，
一个「多智能体协同端云协同系统架构」任务最终难度只有 **0.28（simple）**。

**修复**：
1. 解析键改为「去掉 `root` 的点分路径」（`tech.ai.agent` → 0.60），未覆盖时退回叶子名，最后落 0.20
2. `_lookup_domain_difficulty` 未命中返回 `None` 而非 `0.0`
   —— 否则 `0.0` 会被 `safe_float(x, 0.20)` 当成有效值，把默认值分支吃掉、
   与「难度对回答质量的双层加成」是同一类静默错误
3. 新增回归用例锁定「缺 `skill_path` 时退化为 daily 基线」这一行为

> ⚠️ **这是会改变运行时的行为变更**：修复后 `tech.*` 深层领域任务的难度会正确升高，
> Judge 双阈值矩阵可能**更频繁地判定 `cloud_enhance`**。这是「修对了」的必然结果
> （之前是把复杂任务误判为 simple），但请留意云端用量。若你希望控制成本，
