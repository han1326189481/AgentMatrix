## 一、项目概览

| 维度   | 内容                                                          |
| ---- | ----------------------------------------------------------- |
| 定位   | 桌面级多智能体协作平台，本科毕业设计 + 考研复试答辩项目                               |
| 核心叙事 | 5-Agent 责任链 + 本地/云端混合推理 + 自学习技能引擎 + 认知图谱                    |
| 前端   | Next.js 14（App Router）、React 18、TypeScript、Tailwind、Zustand |
| 桌面壳  | Tauri 2.x（Rust 负责拉起/回收 Python 后端进程）                         |
| 后端   | FastAPI + python-socketio，PyInstaller 打包为单文件 EXE            |

## 二、整体架构

### 2.1 分层架构

自顶向下分为六层，越靠下越靠近资源与算力：

| 层  | 名称     | 承载内容                                                 |
| -- | ------ | ---------------------------------------------------- |
| L1 | 桌面外壳层  | Tauri 2.x（Rust 进程管理）+ Next.js/React/Zustand 前端       |
| L2 | 接入与通信层 | FastAPI REST（16 个子路由）+ WebSocket / Socket.IO 双通道     |
| L3 | 编排层    | `WorkflowService` 责任链 + L1/L2 意图缓存 + 指标与成本埋点         |
| L4 | 智能体层   | Knowledge → Writer → Review → Judge → Result         |
| L5 | 认知内核层  | Skill Engine V2/V3、四类图、引擎集、PersonalBrain、MemoryStore |
| L6 | 模型与数据层 | Ollama 本地模型、DeepSeek 云、Web 搜索插件、SQLite / MySQL       |

**依赖方向是单向自顶向下**：`api` → `core.workflow` → `agents` → `core.engines / core.graphs` → `core.llm / knowledge`。这个方向整体是干净的，没有出现底层反向 import 上层的情况（唯一的横向耦合是 `api/v1/chat` 直接 import `api/v1/workflow` 的 `execute_workflow` 与 `api/v1/config` 的 `_runtime_config`）。

### 2.2 运行时拓扑

```
用户
 └─ Tauri 窗口（WebView 加载 Next.js 前端）
      ├─ HTTP  →  127.0.0.1:8000  FastAPI（REST）
      └─ WS    →  127.0.0.1:8000  /ws  与  socket.io
                        │
            内嵌 Python 后端进程（agentmatrix-backend.exe 或 uvicorn）
                        ├─ Ollama  127.0.0.1:11434（本地推理）
                        ├─ DeepSeek api.deepseek.com（可选云增强）
                        ├─ cn.bing.com / sogou.com（Web 搜索，正则解析）
                        └─ SQLite（storage/agentmatrix.db + storage/sandboxes/*.db）
```

Rust 侧的进程生命周期管理是本项目工程完成度较高的部分：指数退避拉起（`lib.rs`，`[1,2,4,8,10,10]`，6 次失败后永久放弃）、`wait_for_ready` 轮询 `/health` 最长 90s、窗口 `CloseRequested` 时先温和 `taskkill` 等 5s 再强制结束。**唯一危险点是 `free_port_8000()` 用 `taskkill /F` 强杀任何占用 8000 端口的进程**，属于误杀设计。

### 2.3 工作流数据流

```
用户输入（文本 + 可选图片）
   ↓
Knowledge Agent   知识库检索 / 时效性话题触发 Web 搜索 / 图片触发视觉插件
   ↓              （产出 knowledge_items、skill_path、task_data）
Writer Agent      注入 skill 上下文 + 7 维用户画像，生成本地正文
   ↓
Review Agent      质量评分 review_score(0-1) + 难度 difficulty(0-1) + 弱维度
   ↓
Judge Agent       双阈值矩阵决策（纯规则，不调用 LLM）
   ↓
   ├── local_output   难度 < 0.50，或难度/评分组合满足本地阈值
   ├── polish         云端润色（0.65 > 难度 ≥ 0.50 且评分偏低）
   └── full_rewrite   云端重写（难度 ≥ 0.80，或 0.80 > 难度 ≥ 0.65 且评分 < 0.80）
   ↓
Result Agent      格式化 + 云端增强 + 失败回退为 Writer 原文
   ↓
最终输出（WebSocket 实时推送前端）
```

除主链外还有**两条旁路**：

- **反馈旁路**：Review 输出回流 Skill Engine，构成自学习闭环。
- **澄清旁路**：检测到抱怨（5 类关键词）时中断主链，生成道歉 + 3~5 个带 A/B 选项的澄清问题，弹窗期间暂停工作流。

## 三、核心设计思路

项目的设计思路可以概括为"**用架构设计换取硬件约束下的可用性**"——在 8GB 显存、无 GPU 集群的消费级硬件上，通过职责分离与智能路由逼近云端体验。

### 3.1 责任链式多智能体：为什么是 5 个

不是"多 Agent 就更好"，而是把一次生成的**四个认知动作**显式拆开：

| Agent     | 认知动作    | 为什么必须独立                 |
| --------- | ------- | ----------------------- |
| Knowledge | 我需要什么信息 | 检索成本高、可缓存，需与生成解耦        |
| Writer    | 写出初稿    | 唯一需要大上下文的环节             |
| Review    | 这稿子行不行  | 需要"跳出生成"做评价，同一模型自评不准    |
| Judge     | 要不要动用云端 | 纯规则、零 token 成本，必须可预测可审计 |
| Result    | 怎么交付    | 格式化与降级回退，与内容生成无关        |

关键设计选择是 **Judge 不调用 LLM**：路由决策用规则矩阵而非模型判断，好处是零成本、可复现、可解释；代价是阈值需要人工调参（这也是文档与实现出现偏差的根源之一）。

### 3.2 本地优先 + 混合推理

双阈值（难度 + 评分）而非单阈值，是因为**单看"难度"会漏掉"简单但答得差"的情况**。额外加了两层修正：

- **强信号词修正**：检测到 ≥2 个复杂度信号词时，把难度强制抬到 0.70，用来对抗小模型普遍低估任务难度的问题——这是很务实的一招。
- **弱维度感知路由**：根据 Review 指出的弱维度（准确性/专业性/完整性）决定用 `polish` 还是 `full_rewrite`，而不是无差别重写。
- **优雅降级**：无 API Key 时 `cloud_enhance` 自动退化为 `local_output`；云端调用失败时保留 Writer 原文。

### 3.3 图优先、引擎其次

设计口号是"知识表示为图，引擎只是图的调用方"。四类图的**设计意图**分别是：

- **Skill Graph**：技能层级与关联，支撑技能路径检索与自学习增补
- **Capability Graph**：追踪用户能力掌握进度，与用户画像联动
- **Reasoning Graph**：推理路径模式复用
- **Intent Graph**：意图理解与消歧

这个思路本身是成立的——把知识从"散落在代码里的 if-else"提升为"可持久化、可增删、可演化的数据结构"。**问题在于落地程度参差**（详见 4.2）。

### 3.4 自学习闭环

闭环链路设计为：Review 反馈 → 置信度过滤（≥0.85）→ 弱维度聚合（同领域 ≥3 条）→ 生成约束/禁令/建议关键词 → 半自动应用（默认待审、高置信可自动应用并升版本）。

### 3.5 用户建模：双子系统分工

- **PersonalBrain（7 维画像）**：identity / goals / preferences / 表达风格 / 学习阶段 / abilities / context，存 `storage/profiles/{user_id}.json`，通过 `build_context()` 注入 Writer。
- **MemoryStore（长期记忆）**：容量 200，淘汰分 = `importance*0.6 + recency*0.25 + access*0.15`，importance < 0.3 不入库。
- **MemoryExtractor**：用 1.5B 小模型异步抽取事实/偏好/目标/事件，零云成本，失败回落规则抽取。

分工是清晰的：画像回答"用户是谁"，记忆回答"用户说过什么"。

### 3.6 数据隔离与交付

- **多沙箱**：每个沙箱一个物理 SQLite 文件，全局库只存元数据；支持软删除 + 物理清理。
- **多格式导出**：DOCX 走 pandoc，PPTX 走 marp-cli，思维导图走 markmap-cli，均带纯 Python 降级方案。优先"用行业标准工具"而不是手写解析器，这个取舍是对的。

## 五、改进路线图

### 阶段一：止血（安全与可用性，预计 1~2 天）

1. **加全局鉴权**：生成一个本地 token 存 `%APPDATA%`，FastAPI 加一层 `Depends` 中间件校验；Tauri 启动时把 token 注入前端。这是最低成本的最大收益。
2. **收紧 CORS**：`allowed_origins_list` 默认值由 `"*"` 改为显式白名单，且 `allow_credentials` 与通配符不可同时开启。
3. **修路径穿越**：把 `export/router.py` 四处写文件入口统一走一个 `_safe_join(EXPORT_DIR, filename)` 校验函数（可直接复用 `:135` 已有的判断逻辑）；`platform.py:119` 对 `sandbox_id` 做 `[A-Za-z0-9_-]` 白名单过滤。
4. **`.env` 移出打包清单**：从 `agentmatrix.spec:20` 删除 `('.env', '.')`，改为运行时由用户输入写入 APPDATA。
5. **修 `free_port_8000`**：只杀自己启动的进程（记录 PID），不要无差别 `taskkill /F`。

### 阶段二：结构收敛（预计 1 周）

1. **拆分 `service.py`**：抽出 `CacheCoordinator` / `MetricsCollector` / `StepRunner`，让 `execute` 只负责编排；`execute_stream` 与 `execute` 合并为同一内核 + 两种输出适配器。
2. **结束"失败伪造"**：为 Agent 输出引入显式 `AgentStatus`（ok / degraded / failed），Review 失败时如实标记并让 Judge 走保守路径，而不是编造 0.7 分。
3. **清理硬编码**：`user_id` 从请求上下文取；`skill_path` 默认值提到配置；阈值统一进 `configs/` YAML。
4. **清理仓库**：删除根目录重复的 `prompts/`、`knowledge/`、`configs/`、`shared/`；把 `backend/libs/` 改为 `requirements.txt` 声明 + 构建脚本按需 vendoring，或把 vendoring 步骤写进 CI；删除 14 个启动脚本只保留 2 个（开发 / 生产），并统一入口为 `app.main:socket_app`。
5. **提交分界**：把当前 23 个修改 + 16 个未跟踪文件整理成 2~3 个语义化 commit。

### 阶段三：兑现叙事（预计 2~3 周）

1. **给图补算法**：这是答辩加分点也是当前最大短板。
   - `SkillGraph.search_by_name` 建倒排索引，从 O(N) 降到 O(1)；补最短路 / 拓扑排序 / 中心性。
   - `ReasoningGraph` 真正引入边结构，把"推理模式复用"做成可遍历的路径。
   - `CapabilityGraph` 落盘持久化。
   - `IntentGraph` 至少升级为带边的意图转移图。
2. **打通自学习闭环**：实现 `LearningEngine._deepseek_analyze`；把 `_pending_patches/` 的 33 个孤儿 patch 接进审核流程，或明确删除 V2 断链并在文档中说明 V3 为唯一实现。
3. **引入数据库迁移**：加 Alembic；修复 MySQL 分支的 `SessionLocal` 未初始化；沙箱引擎加池化上限。
4. **补并发正确性**：给缓存与共享图谱加锁（或改为 per-request 实例）；把 `_runtime_config` 从全局可变 dict 改为请求级依赖注入。
5. **加最小 CI**：GitHub Actions 跑 `ruff` + `pytest`（当前 94 个测试文件在有 CI 后才有意义）。

## 六、总结

**做得好的地方**（应当在答辩中主动强调）：

- **分层清晰、依赖方向干净**，六层架构没有出现底层反向依赖，模块边界经得起推敲。
- **工程完成度高于同类毕设**：Tauri 桌面壳的进程生命周期管理（指数退避、就绪轮询、优雅关闭）做得相当扎实；前端类型定义与后端 Pydantic 契约基本对齐，全项目仅 2 处 `any`；导出走 pandoc/marp/markmap 行业标准工具并带纯 Python 降级。
- **设计取舍务实**：Judge 用纯规则换取零成本可审计、强信号词修正对抗小模型低估难度、失败逐级降级保底返回原文——这些都是"在 8GB 显存约束下真实思考过"的痕迹。
- **有真实闭环的雏形**：SkillGraph 是真图且有 636 节点 / 435 边；V3 LearningEngine 已能产出并落盘自学习节点。

**最需要改进的地方**（按投入产出比排序）：

1. **安全**：无鉴权 + CORS 通配 + 两处路径穿越 + Key 打进 EXE——这四项是硬伤，且修复成本都不高。
2. **可观测性**：失败被伪造成 0.7 分、异常被静默吞没，导致系统"看起来永远正常"，这会让调试和演示都变成盲盒。
3. **架构叙事的兑现度**：四个图里只有一个是真的，"图优先"目前更像设计意图而非实现事实；自学习 V2 是断链。这两点恰好是项目最核心的卖点，建议要么补齐、要么在文档中诚实地重新界定范围。
4. **工程卫生**：巨型文件、重复目录、14 个冲突脚本、无 CI——不影响功能，但严重影响可维护性与他人复现。

**一句话结论**：AgentMatrix 的**架构设计水准明显高于其实现水准**。把 P0 安全问题和 P1 中的"失败伪造 / 图名实不符"解决掉，这个项目就从"一个想法很多、细节粗糙的毕设"变成"一个经得起追问的完整系统"。
